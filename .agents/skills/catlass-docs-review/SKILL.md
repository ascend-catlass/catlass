# CATLASS 文档语言审查

本技能负责 Markdown 文档的语义级审查与修订：术语、用词、错别字、量化判据、事实来源、数值单位、结构与语气。仓库约定与强制规则见根 [`AGENTS.md`](../../../AGENTS.md)，英文同步由 `catlass-docs-translation` 负责。

## 触发条件

满足任一条件即执行本技能：

- 新增、修改或删除任意 `*.md`：`docs/zh/**`、`docs/en/**`、根目录 `README*.md`、`AGENTS.md`、`examples/**/README.md`、`.agents/skills/**/SKILL.md`。
- 文档中的数值、规格、示例或结论被改动，需要核对同文档内相关表述是否同步。
- 提交前、创建 PR 前、评审 PR 时。
- 用户要求检查文档质量、术语、错别字、表述或量化问题。

不触发：纯代码改动且无文档变更；仅行尾空白、文件末尾换行等格式问题（交给仓库 `pre-commit` 静态检查）；仅外链可达性（交给 `scripts/check_md_links.py`）。

## 静态检查与模型检查的分工

静态问题全部交给 `pre-commit run --files <改动文件>`：空白、换行、YAML/JSON 语法、相对链接与锚点等都在其 hook 覆盖范围内。

- 可自动修复的直接采用，无法自动修复的按报错手工修复；静态问题清零后再做语言审查。
- 本技能只处理 pre-commit 无法判定的语义问题：术语、错别字、量化判据、规格来源、单位、结构与语气。
- 能用固定规则判定的问题优先由 pre-commit hook 覆盖。

## 审查范围

只审改动 hunk 及受其直接影响的同文档内容（同一术语、同一数值、同一表格、同一结论）。不重写未改动段落，不做与本次改动无关的润色。

## 工作流

1. 取改动范围：

   ```bash
   git diff --unified=0 HEAD -- '*.md'                    # 工作区
   git diff --unified=0 upstream/master...HEAD -- '*.md'  # 已提交
   ```

2. 先执行 `pre-commit run --files <改动文件>`：可自动修复的问题直接采用修复结果；无法自动修复的按报错逐条手工修复。静态问题清空后再进入下一步。
3. 按下方清单逐块检查，先记录问题再改，避免边读边改导致遗漏。
4. 输出问题清单（格式见末节），确认问题分类与建议改文。
5. 最小改动修复；同一错误在全文重复出现时一并修正，避免只改一处。
6. `docs/zh/**` 有改动时，按 `catlass-docs-translation` 同步英文文档。
7. 复跑静态检查并报告结果：

   ```bash
   pre-commit run --files <改动文件>
   ```

## 问题分类

审查结论按以下 8 类归档：

| 分类 | 判定标准 |
| ---- | -------- |
| 术语与参数定义缺失 | 术语未定义、同一概念多种叫法、参数含义未说明 |
| 内容缺失与结构不完整 | 缺少前提、步骤、边界条件或结论 |
| 判定标准与操作路径缺失 | 只说要判断/优化，未给出判据或操作入口 |
| 缺乏量化 | 收益、开销、影响无任何数值或范围 |
| 量化不精确 | 有「约数、显著」等表述但无阈值、无来源 |
| 数据来源与可复现性缺失 | 规格值、实测值无型号、无出处、无复现条件 |
| 格式与表达不一致 | 单位、大小写、编号、层级、代码块语言不统一 |
| 反例缺失 | 只给正例，未说明不适用场景或误用后果 |

## 审查清单

### 1. 产品与术语写法

| 正确写法 | 常见错误写法 | 说明 |
| -------- | ------------ | ---- |
| `Atlas A2` / `Atlas A3` | `AtlasA2` / `AtlasA3` | 产品名，中间必须带空格 |
| `Ascend 950` / `Ascend 950PR` / `Ascend 950DT` | `Ascend950` / `Ascend950PR` | 产品名，中间必须带空格 |
| `Atlas A2系列产品、Atlas A3系列产品` | `Atlas A2/A3产品` | 同时指代 A2、A3 两代产品时的合写形式；单独指代仍用 `Atlas A2` / `Atlas A3` |
| `Ascend 950PR&950DT系列产品` | `Ascend 950PR/Ascend 950DT产品` | 同时指代 950PR、950DT 时的合写形式 |
| `AI Core` | `AICore` | 计算核心，中间必须带空格 |
| `Ascend C` | `AscendC` / `asc-devkit` | 正文写法必须带空格；仅 C++ 命名空间 `AscendC::` 保持无空格原样；不使用 `asc-devkit` 指代 Ascend C |
| `Flash Attention` | `FlashAttention` | 正文写法带空格；仅代码标识符/样例名（如 `FlashAttentionInfer`）保持原样 |
| `L2 Cache` | `L2Cache` | 缓存名称带空格；仅 profiling 产出文件名 `L2Cache.csv` 保持原样 |
| `Cube Core` | `Cube-core` | 不带连字符 |
| `CANN toolkit` | `CANN开发套件包` | CANN 开发套件包统一写作 `CANN toolkit` |
| `Padding` | `padding` | 工程优化项名称首字母大写，如「读取带宽优化(Padding)」 |
| `PIPE_FIX` | `PIPE_FIXED` | Ascend C 流水类型枚举值；勿臆造 `PIPE_FIXED` |

代码形式优先：术语位于代码块或行内代码中时保持代码原样，不补空格、不拆分；仅正文、标题、表格文字按上表更正。

- 产品与项目名保持原样：`CATLASS`、`CANN`、`TLA`、`Ascend`、`Atlas A2 and Atlas A3`、`Ascend 950`；不使用代号式替换。
- API、类、函数、宏、文件路径、命令、环境变量、URL、锚点、代码标识符保持原样，不翻译、不改写。

### 2. 中文错别字与用词

| 正确写法 | 常见错误写法 | 说明 |
| -------- | ------------ | ---- |
| 显式补零 | 显示补零 | 「显式」表示明确指定 |
| 归约（ReduceAdd） | 规约 | 并行累加统一用「归约」 |
| 分形 | 分型 | L0/L1 上的 16*16、16*32 数据块统一称「分形」 |
| 起始地址 | 其实地址 | |
| 受到影响 | 收到影响 | |
| 微缩放（MX Scale） | 微缩缩放 | |
| 不再 | 不在 | 「不再（no longer）」 |
| 该值 | 改值 | 「该值（this value）」 |
| 在 … 上 | 再 … 上 | 表示位置或载体时用「在」 |
| 不同的是 | 不同地 | 「与 … 不同的是」为固定搭配 |
| 简洁地描述 | 简洁的描述 | 修饰动词用「地」 |
| 使用 | 完成使用 | 去除冗余动词 |
| 启用 | 使能 | enable 系列、编译选项、特性开关统一用「启用」；「开启」「打开」保持原样 |
| 无法 | 没法 | 书面表述不用口语 |
| 详细使用示例…请参考 | 详细参考使用示例…请参考 | 去除重复的「参考」 |

### 3. 英文拼写易错项

| 正确写法 | 常见错误写法 | 说明 |
| -------- | ------------ | ---- |
| `utilities` / `utility` | `utilties` / `utilty` | 标题与正文拼写 |
| `TreeVisitor` | `TreeVistor` | EVG 访问者节点名 |
| `ColumnMajor` | `ColumMajor` | 矩阵布局名 |
| `DataCopy` | `Datacopy` | Ascend C 数据搬运接口名 |
| `GetTile` | `Getile` | TLA 取 Tile 接口名 |
| `loadDataParams` | `loadDataPrams` | 结构体变量名 |
| `block` | `bloc` | |
| `width` | `wight` | 参数含义注释 |
| `true` | `ture` | 布尔字面量 |
| `CPU` | `cpu` | 缩写统一大写 |

英文表达：

- 术语沿用同一篇及相邻文档的既有英文表达；没有可靠先例时使用简洁技术英语，不凭空扩展缩写或命名。
- 使用清晰的技术说明语气，保留原有 Markdown 层级、链接结构和示例格式。

### 4. 数值与单位

- 浮点算力用 `TFLOPS`，整数或未区分类型的算力才用 `TOPS`；同一句内不得混用（如 FP16 写 11.06TFLOPS，不写 11.06TOPS）。
- 带宽区分 `GB/s`（Byte）与 `Gb/s`（bit）；容量区分 `KB/MB/GB` 与 `KiB/MiB/GiB`。
- 时间单位统一 `μs`、`ms`，正文不用 `us` 代替 `μs`；`Byte`、`bit`、`Element` 首字母大小写与仓库既有文档一致。
- 乘号统一用 `*`，不用全角乘号；连续出现多个 `*` 时用行内代码包裹（如 `4096*4096*4096`），避免被解析为斜体。
- 派生数值必须与所引用的基准值一致：修改带宽、算力、频率等基准后，重算同文档内所有示例并同步结果。例：带宽由 1.8TB/s 改为 1.6TB/s 后，`2Byte*4096*4096` 的搬运耗时由 18.64μs 改为 20.97μs。
- 数值与结论一一对应：正文引用「约 N μs」时必须能由文中公式与规格值复算得到。

### 5. 量化与判据

- 禁止无判据的模糊表述：约、大约、显著、明显、远大于、基本、通常、较大、较低、足够、很快。若确需保留，必须给出阈值、区间或实测依据。
- 量化结论须可执行，例如搬运耗时比按 `≤1.5` 正常、`1.5~2` 需检查、`>2` 重复搬运分档，而不是「偏高」「偏低」。
- 阈值须说明来源：官方实测（附链接）、模板参数推导（如 `k1=256`、`GetSplitkFactor` 分档）、或标注为经验值并写明适用条件（核数、TileShape、数据类型）。
- 收益类结论给出比例或适用数量范围，例如「基本块数 ≤12 且 K>5120 时收益明显」。
- 经验阈值写明「AIC 核数或 `k1` 不同时需按比例重新评估」。

### 6. 事实来源与可复现性

- 硬件规格（带宽、算力、Buffer 容量、核数、频率）必须标注适用型号与官方出处，优先 `hiascend.com`、`support.huawei.com`、`e.huawei.com`。
- 无官方页面时给出折算依据（如 `每拍 256 Byte * 核数 * 主频`）或查询接口（`platform_ascendc::GetCoreNumAiv`、`npu-smi info`），不得只给孤立数值。
- 社区文章、博客、二手转载不作为规格值的唯一来源。
- 规格值变更时全文检索该数值及其派生值，一并更新。
- 外链不能仅凭 HTTP 200 判定有效：SPA 站点对任意路径返回同一外壳页，需比对落地 URL 或正文标题是否匹配。

### 7. 结构与格式（语义部分）

- 标题层级逐级递增，不从 H3 跳到 H5；有序列表编号连续。
- 代码块语言标记与内容一致：C++ 用 `c++`，回显、目录树用 `text`，配置用 `json` 等；`json` 块内不得出现 `//` 注释。
- 命令行参数使用 ASCII 连字符 `--`，不混入 en-dash `–`。
- 使用 `<img>` 时补充 `alt` 属性。
- 相对链接与锚点层级正确；重命名标题后同步更新锚点引用。
- 示例代码须与可编译形式一致：模板参数、逗号与标识符拼写无误（如模板参数列表末尾逗号、`loadDataParams`）。
- 同一概念全文同名，不引入同义词替换。
- 术语首次出现给出定义或链接，后文直接使用。

### 8. 语气与内容边界

- 不使用「您」「请」「建议」等说教式用语，改用陈述句。
- 文档面向开源社区读者，只写公开可验证的技术结论与可执行事实；不引入需求或任务安排、开发过程叙事、调研过程等与读者无关的背景信息。
- 不臆造标准编号、版本号、接口名或规格值；无法确认时标注待确认，不虚构来源。

## 输出格式

审查结论按问题清单输出，修复后标注状态：

| 文件:行 | 分类 | 原文 | 问题 | 建议改文 |
| ------- | ---- | ---- | ---- | -------- |
| `docs/zh/1_Practice/...:153` | 数据来源与可复现性缺失 | 假设GM峰值带宽约1.8TB/s | 未说明适用型号与出处，且与官方 1600GB/s 不符 | 以Atlas A2训练系列产品为例，其片上内存峰值带宽为1600GB/s |

修复完成后给出：改动文件、问题数量（按分类统计）、已修复与未修复项、`pre-commit` 结果。

## 与其他检查的边界

| 检查项 | 负责方 |
| ------ | ------ |
| 空白、换行、语法、相对链接与锚点等静态问题 | 仓库 `pre-commit` |
| `docs/zh/**` 改动的英文同步 | `catlass-docs-translation` |
| 术语、错别字、量化判据、来源、单位、结构语义、语气 | 本技能 |
