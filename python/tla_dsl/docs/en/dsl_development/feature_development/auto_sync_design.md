# AutoSync Design

## Background and Goals

The MTE, Cube, Vector, Fixpipe, and other pipelines on an Ascend AI Core can execute asynchronously. When the same on-chip storage is read and written in succession by different pipelines, missing or incorrect synchronization produces RAW, WAR, or WAW data races. Manual synchronization requires developers to maintain the storage relationships of tensors, the pipe that each instruction belongs to, double-buffer switching, and the `unit_flag` protocol at the same time; it is verbose and easy to overlook when the algorithm changes.

CATLASS Python provides experimental automatic synchronization through `@tla.kernel(auto_sync="v0")`.

`v0` only handles intra-core synchronization among the pipelines within a single AIC or AIV. It does not generate Cube/Vector inter-core synchronization, nor the synchronization inside a VF in Vector core programming.

## User Interface and Usage Constraints

### How to Enable

Enable it as follows:

```python
@tla.kernel(auto_sync="v0")
def kernel_func(...):
    # No longer hand-write set/wait_flag, mutex, or mutex_guard.
    ...
```

The current public interface accepts only `None` and `"v0"`:

| Configuration | Behavior |
|------|------|
| `@tla.kernel` / `@tla.kernel()` | AutoSync is not enabled; intra-core synchronization is described explicitly by the developer. |
| `@tla.kernel(auto_sync="v0")` | Enables automatic intra-core synchronization. |

For a complete end-to-end sample, see [basic_matmul_auto_sync.py](../../../../../../examples/python/tla_dsl/tla/kernel/matmul/basic_mmad/basic_matmul_auto_sync.py). That sample uses L1 and L0 double buffering and writes no synchronization primitives explicitly in the kernel.

### Usage Constraints

`auto_sync="v0"` adopts a conservative static analysis strategy. Developers must follow the constraints below; when the compiler cannot prove that synchronization is safe, it terminates compilation directly and reports a diagnostic.

| Constraint | Rule the developer must follow |
|--------|----------------------|
| Applicable entry | `auto_sync` is supported only on `@tla.kernel` and cannot be used on `@tla.jit` or other functions. Currently only the version value `"v0"` is supported. |
| Synchronization scope | Only intra-core synchronization among different hardware pipelines within a single AIC or AIV is handled automatically. AIC/AIV inter-core synchronization still requires explicit `cross_flag` and `cross_core_*`; the thread-level synchronization needed inside `tla.vec.func` is not generated automatically. |
| Hand-written synchronization | Once enabled, intra-core `tla.flag`, `tla.set_flag`, `tla.wait_flag`, `tla.mutex`, or `tla.mutex_guard` cannot be used in the same kernel; otherwise compilation fails. |
| Instruction coverage | `v0` analyzes only `tla.copy`, `tla.mmad`, and supported UB accesses inside `tla.vec.func`. AutoSync does not currently support writing UB `scalar_load` / `scalar_store` directly under `tla.vector`; when `v0` is enabled they must be placed inside `tla.vec.func`. Such usage is still legal when AutoSync is not enabled. `tla.print_tensor` and `tla.debug_print` do not receive automatic synchronization. |
| On-chip memory origin | An on-chip tensor protected by automatic synchronization must be traceable back to a static allocation root generated by `tla.allocate`. Constructing recast, offset, tensor, and tile views based on that root is allowed; constructing a tensor through `tla.make_ptr` from a bare on-chip address, and thus being unable to trace back to the allocation root, is not supported. |
| External calls | `v0` cannot be combined with `tla.call_extern`, because the compiler cannot analyze the asynchronous memory accesses and completion semantics inside an external function. |
| Dynamic buffers | Selecting among multiple buffers created by `tla.allocate` through runtime conditions is supported. `v0` does not currently support using an on-chip pointer as loop state and switching it to another allocation during iteration; when a single instruction uses multiple conditionally selected buffers, each branch must also keep a consistent allocation order. |
| `unit_flag` | `tla.mmad` only accepts a `unit_flag` that can be statically proven to be 0 or to always lie in `{2, 3}`; the `CopyL0C2DstParams.unit_flag` of an L0C copy supports only 0 or 3. Switching between 0 and 2/3 at runtime is not supported. |

If a kernel cannot satisfy the constraints above, keep `auto_sync=None` and let the developer describe the required intra-core and inter-core synchronization explicitly.

## Design Boundaries

### What `v0` Is Responsible For

- the on-chip source and destination tensors involved in `tla.copy`;
- the L0A and L0B of `tla.mmad`, and the L0C whose inclusion is decided by the `unit_flag` rules;
- the UB tensors accessed by `tla.load`, `tla.store`, `tla.gather`, `tla.scalar_load`, and `tla.scalar_store` within one `tla.vec.func`;
- recast, offset, tensor, and tile view aliases derived from the same `tla.alloc_ptr`;
- statically traceable runtime conditional buffer selection.

### What `v0` Is Not Responsible For

- inter-core synchronization between AIC and AIV;
- asynchronous accesses that may occur inside `tla.call_extern`;
- synchronization of `tla.print_tensor` and `tla.debug_print`;
- bare on-chip addresses or pointers that cannot be traced back to a static `tla.alloc_ptr`;
- using an on-chip pointer as loop state and switching it to another allocation during iteration;
- mixing hand-written intra-core synchronization with automatic intra-core synchronization.

Therefore, after `v0` is enabled, using intra-core `mutex`, `mutex_guard`, `flag`, `set_flag`, or `wait_flag` in the same kernel is forbidden.

The inter-core `cross_flag`, `cross_core_set_flag`, and `cross_core_wait_flag` are not subject to this restriction.

## Compilation Pipeline

AutoSync's control information travels from the CATLASS Python decorator all the way to the MLIR pass:

```text
@tla.kernel(auto_sync="v0")
          │
          │ catlass/dsl.py validates and saves options
          ▼
execution_lowering.py constructs tla.func
          │ adds {tla.auto_sync = "v0"}
          ▼
TlaLowerFuncPass
          │ tla.func -> func.func, keeps the attribute and determines the AIC/AIV/MIX type
          ▼
TlaInsertAutoMutexPass
          │ analyzes allocation roots, instruction resources, and pipes
          │ inserts tla.mutex / lock / unlock, removes the tla.auto_sync attribute
          ▼
TlaLowerPtrPass / TlaSplitMixedFuncPass / region lowering
          ▼
TlaLowerMutexToStdPass
          │ !tla.mutex -> i8 ID
          │ lock/unlock -> get_buf_<pipe> / rls_buf_<pipe> runtime call
          ▼
backend compilation and bitcode linking
```

The key order is that `TlaInsertAutoMutexPass` sits after `TlaLowerFuncPass` and before `TlaLowerPtrPass` and `TlaSplitMixedFuncPass`:

- `TlaLowerFuncPass` has already derived the function core type from the `tla.cube` / `tla.vector` regions;
- the `tla.alloc_ptr`, tensor/view chains, and structured control flow have not yet been broken, which suits resource tracing;
- the MIX kernel has not yet been split into two AIC/AIV functions, so the pass can build the Cube and Vector mutex ID spaces separately on the same original structure.

Corresponding implementation entry points:

- Python interface: [catlass/dsl.py](../../../../catlass/dsl.py)
- Attribute generation: [catlass/execution_lowering.py](../../../../catlass/execution_lowering.py)
- Pass pipeline: [PassRegistry.cpp](../../../../csrc/mlir/lib/Passes/PassRegistry.cpp)
- AutoSync core: [TlaInsertAutoMutexPass.cpp](../../../../csrc/mlir/lib/Passes/TlaInsertAutoMutexPass.cpp)
- mutex lowering: [TlaLowerMutexToStdPass.cpp](../../../../csrc/mlir/lib/Passes/TlaLowerMutexToStdPass.cpp)

## Core Model

### The allocation root is the identity of the synchronization resource

AutoSync does not use the tensor SSA value as the resource identity; it uses the on-chip memory's `tla.alloc_ptr` root as the identity. The reason is that multiple tensors/views may reference the same physical storage:

```text
%root = tla.alloc_ptr ...
   ├── tla.recast_ptr
   ├── tla.ptr_add
   └── tla.make_tensor / tla.make_tensor_like
          └── tla.tile_view
```

These derived values all resolve to `%root` in the end and share the same mutex. A tensor's dynamic shape, stride, or coord does not change the allocation root, so a mutex is not allocated again just because the view shape differs.

`TlaScratchAllocation` records for each root:

- address space;
- alignment;
- the statically allocated `[base, end)` byte range;
- allocation size.

AutoSync and the later `TlaLowerPtrPass` share the result of `planTlaScratchAllocations()`, ensuring that the resources described by a mutex are consistent with the physical on-chip addresses finally lowered.

GM and generic memref are treated as global resources and are not allocated an intra-core mutex; if an on-chip resource cannot be resolved to a valid root, compilation fails.

### An instruction is the locking boundary

Each supported asynchronous instruction forms an `InstructionPlan`:

```text
InstructionPlan = {
    op,          // the instruction corresponding to the locking range
    pipe,        // the hardware pipeline executing the instruction
    idSpace,     // the Cube or Vector mutex ID space
    resources,   // the on-chip allocation roots accessed by the instruction
}
```

The resource collection rules are as follows:

| Instruction boundary | pipe | Resources included |
|----------|------|------------|
| `tla.copy` with a GM source | `mte2` | the on-chip dst |
| `tla.copy` with an L1 source | `mte1` | the on-chip src and dst |
| `tla.copy` with a UB source | `mte3` | the on-chip src and dst |
| `tla.copy` with an L0C source | `fix` | the on-chip src and dst, plus the quant scale passed as a tensor; when `unit_flag=3` the L0C is handled by the unit flag protocol and is not locked again |
| `tla.mmad` / `tla.mmad_mx` | `cube` | L0A, L0B, and the bias (when `bias` is supplied); also the L0C accumulator when the unit flag is not enabled |
| `tla.vec.func` | `vector` | the UB roots accessed by load/store/gather/scalar load/store in the region, locked uniformly after deduplication |

GM operands are filtered out during resource normalization. When one instruction accesses the same root multiple times, it is locked only once.

### Insertion form

Suppose an L1-to-L0A copy accesses both `%l1` and `%l0a`; the core structure before and after the pass is:

```mlir
// before
tla.copy %l0a_tensor, %l1_tensor

// after (schematic)
%l1_mutex = tla.mutex "auto_l1_0_4096" {id = 0 : i64}
%l0a_mutex = tla.mutex "auto_l0a_0_4096" {id = 1 : i64}
tla.mutex_lock %l1_mutex[<mte1>]
tla.mutex_lock %l0a_mutex[<mte1>]
tla.copy %l0a_tensor, %l1_tensor
tla.mutex_unlock %l0a_mutex[<mte1>]
tla.mutex_unlock %l1_mutex[<mte1>]
```

The mutex declarations are placed uniformly at the function entry. Locks are acquired in stable ID order and released in the reverse order, forming a stack-like order that avoids lock-order inversion among multi-resource instructions.

## mutex ID Allocation

### Cube and Vector use independent spaces

Hardware mutex IDs are managed independently by core side. AutoSync collects the actually used allocation roots for Cube and Vector separately and allocates IDs from 0 for each. A MIX kernel can have both a Cube-side `id=0` and a Vector-side `id=0`, and the two are not the same cross-core synchronization object.

Each side uses at most 32 automatic mutex IDs. Exceeding the limit reports an error at compile time.

### Deterministic ordering

Resources on the same side are sorted first by address space, then by static base. The address space order is fixed as:

```text
L1 < L0A < L0B < L0C < UB < biasbuf
```

Deterministic ordering has two purposes:

- the IR and test results do not depend on traversal or hash-table order;
- all multi-resource instructions share a unified lock order, reducing the risk of deadlock.

A mutex's debug name is `auto_<address-space>_<base>_<size>`, for example `auto_ub_256_256`. The name is for readability; what is actually passed to the runtime is the numeric ID.

## Dynamic Control Flow

### `scf.if` selection

Double buffering usually selects different allocations based on a runtime condition:

```python
buf = buf0_ptr if index == 0 else buf1_ptr
tensor = tla.make_tensor_like(buf, source)
tla.copy(tensor, source)
```

After lowering to `scf.if`, the true root of the pointer can only be determined at runtime. AutoSync does not conservatively lock both candidate mutexes at once; instead it adds a parallel `!tla.mutex` result to the original `scf.if`:

```text
                  then: (buf0_ptr, mutex0)
condition ─ scf.if
                  else: (buf1_ptr, mutex1)
                             │
                             └── copy uses the selected mutex
```

The mutex and the pointer propagate along exactly the same control flow, which preserves precision and also avoids the dominance problems caused by reconstructing a branch-local condition at the instruction site. A nested `scf.if` materializes the corresponding mutex result from the inside out.

### Loop-carried values

For an `scf.for` iter argument/result, the root is considered stable only when the initial value and the backedge both resolve to the same storage expression. When each iteration of the loop switches to a different root, or the provenance cannot be proven consistent, `v0` refuses to compile.

### Combination constraints for multiple dynamic buffers

When one instruction accesses multiple buffers selected by runtime conditions at the same time, each branch must keep a consistent allocation order. For example, if one branch selects `buffer0` as src and `buffer1` as dst while the other branch conversely selects `buffer1` as src and `buffer0` as dst, `v0` does not currently support this form. The reason is that AutoSync cannot generate a unique and consistent mutex lock order for all runtime branches. This is a current capability limitation of AutoSync, not a general limitation of CATLASS Python on conditional buffers.

## `unit_flag` Coordination

The `unit_flag` of MMAD/FIX already handles part of the L0C pipeline handshake. AutoSync must avoid establishing a duplicate mutual-exclusion protocol for the same resource.

### MMAD

- `unit_flag=0`: the L0C accumulator is included in the mutex together with L0A and L0B;
- `unit_flag=2` or `3`: the L0C is protected by the unit flag protocol, and AutoSync locks only L0A and L0B;
- the bias table has the same standing as L0A and L0B: whenever the MMAD carries a `bias`, it is locked as a `cube` resource alongside L0A and L0B; the `unit_flag` protocol covers only L0C and never exempts the bias;
- obtaining the unit flag through a cast, `arith.select`, or `scf.if` is allowed, but it must be statically provable that it is always 0 or always lies in `{2, 3}`;
- when it may switch between 0 and 2/3 at runtime, whether an L0C mutex is needed cannot be determined, so an error is reported.

### L0C copy

`CopyL0C2DstParams.unit_flag` supports only 0 or 3:

- `unit_flag=0`: both the L0C and the destination on-chip resource are locked by the normal rules;
- `unit_flag=3`: the L0C side relies on the unit flag protocol and AutoSync no longer locks the L0C; the destination on-chip resource still needs to be locked.

In this way, MMAD's enabled unit flag and Fixpipe's `unit_flag=3` can form a complete L0C produce/consume protocol, with the intra-core mutex handling the remaining resources.

## Conservative Failure Strategy and Known Limitations

The principle of `v0` is "generate after proving safe, otherwise fail". Typical limitations and diagnostics are as follows:

| Scenario | Cause/Handling |
|------|-----------|
| Mixing hand-written local flag/mutex | The interaction between the automatic and manual protocols is unclear, so compilation is refused. |
| Using `tla.call_extern` | The pass cannot see the accesses inside the extern or its completion semantics, so compilation is refused. |
| A protected on-chip tensor constructed by `tla.make_ptr` from a bare address | It cannot be traced back to the allocation root, so AutoSync cannot determine its storage ownership and aliasing relationships, and compilation is refused. |
| When `v0` is enabled, switching an on-chip pointer to another allocation between loop iterations | AutoSync cannot currently determine a unique protected buffer for that loop state, so compilation is refused. |
| When `v0` is enabled, writing UB `scalar_load` / `scalar_store` directly under `tla.vector` | AutoSync does not currently support this form; it is still legal when AutoSync is not enabled. |
| One instruction using multiple conditionally selected buffers with inconsistent allocation order across branches | AutoSync cannot currently generate a lock order consistent across all branches, so compilation is refused. |

These limitations deliberately keep the semantics of `v0` simple. If a later version expands the coverage, it should evolve explicitly through a new version value rather than silently changing the meaning of `v0`.

## Test Design

AutoSync's tests are divided into three layers:

1. Python frontend tests verify argument validation, off-by-default, and propagation of the `tla.auto_sync` attribute, see [test_local_autosync.py](../../../../tests/frontend/ops/sync/test_local_autosync.py).
2. MLIR lit tests directly check pass output and failure diagnostics:
   - [auto-mutex-instruction-pipes.mlir](../../../../tests/lit/sync/mutex/auto-mutex-instruction-pipes.mlir): instruction resources, pipes, lock order, and unit flag;
   - [auto-mutex-bias.mlir](../../../../tests/lit/sync/mutex/auto-mutex-bias.mlir): the bias resource of `tla.mmad` / `tla.mmad_mx` and its boundary with the unit flag;
   - [auto-mutex-alias-root.mlir](../../../../tests/lit/sync/mutex/auto-mutex-alias-root.mlir): alias roots;
   - [auto-mutex-dynamic-select.mlir](../../../../tests/lit/sync/mutex/auto-mutex-dynamic-select.mlir): dynamic selection;
   - [auto-mutex-id-spaces.test](../../../../tests/lit/sync/mutex/auto-mutex-id-spaces.test): independent ID spaces and the 32-ID limit;
   - [auto-mutex-diagnostics.test](../../../../tests/lit/sync/mutex/auto-mutex-diagnostics.test): conservative failure paths.
3. `basic_matmul_auto_sync.py` verifies double buffering, the MMAD/FIX unit flag, and the final numerical result end to end.

## Checklist When Extending AutoSync

When adding a new instruction or expanding the automatic synchronization coverage, at least the following questions must be answered:

1. What is the instruction-level synchronization boundary, and on which pipe does the asynchronous completion happen?
2. Which operands read, write, or read-write on-chip resources, and is there an implicit tensor operand?
3. Can the resource be traced back to the `tla.alloc_ptr` root along all legal tensor/pointer constructions?
4. Does the instruction already have a unit flag, barrier, or other hardware handshake that must be avoided duplicating?
5. How are the mutex ID spaces determined in AIC, AIV, and MIX kernels?
6. When a single instruction involves multiple resources, can a globally stable lock order be maintained?
7. Is the provenance still provable under `scf.if` and `scf.for`?
8. Does an unsupported input have a clear diagnostic and a corresponding negative lit test?

In implementation, new rules should preferentially be added to `collectInstructionPlans()`, keeping the three responsibilities of storage provenance, ID allocation, and lock materialization separate, and avoiding spreading the special semantics of one op into the general resource analysis.
