# Structured Kernel Arguments Design

## Background and Goals

A single Python logical argument can contain multiple Tensors, scalars, and static fields, whereas a device function receives formal parameters of determined types and the launcher fills physical ABI fields. Structure recognition, device argument generation, and launch packing must use a consistent order; otherwise, even if every field type is legal, a wrong value may be passed.

This design uses an argument tree to hold the logical structure, leaf bindings to connect device types, and then the `KernelAbiLayout` generated by TypeBridge to determine the launch fields. For usage and capability boundaries, see
[Structured Kernel Arguments](../../kernel_development/core_concepts/structured_arguments.md).

## Argument Tree and Leaf Binding

| Object | What it holds |
| --- | --- |
| `NodeType` | the `to_iterable/from_iterable` splitting and reconstruction rules of one kind of node |
| `PyTreeDef` | the node types, metadata, and ordered subtrees of the current arguments |
| `Leaf` | a runtime binding index, or a constexpr static value and Unit position |
| `RuntimeLeafBinding` | the leaf path, MLIR type, and lowering category |
| `RuntimeArgumentTree` | the tree and ordered runtime bindings of one top-level argument |
| `KernelAbiLayout` | the physical fields, offsets, widths, and logical grouping of the final entry |

Taking `aux = (bias, [0.5, None])` as an example:

```text
tuple
├── child[0] Tensor  → runtime leaf 0
└── child[1] list
    ├── child[0] f32 → runtime leaf 1
    └── child[1] Unit → no runtime leaf
```

Runtime leaves use depth-first, left-to-right order. Node metadata holds the concrete Python type, field names or indices, and static field positions, and does not keep a container sample as a reconstruction template.

The tree is responsible for "where a field is", the binding for "what device type the field is", and the ABI layout for "where it is written at launch".

When building the tree, `RuntimeLeafBinding`s are generated in DFS order, and at runtime `Leaf.binding_index` points to the corresponding binding. The MLIR type is kept in the binding and is not re-derived at launch.
Lowering generates the actual argument type list by binding category, and allocates slots by the list length: an ordinary leaf is 1 block argument, and Dynamic-GM is 3.
`RuntimeLeafBinding.kind` selects the leaf's lowering and reconstruction method and does not represent the final physical ABI type.

`TreeMetadata` holds the node type, field names, child keys, and static field positions.
The number of children is taken directly from the length of the child keys, and static field names are obtained by position; static values are kept in constexpr leaves.

## Compilation and Launch Flow

Following the user guide's `add_bias(x, aux, out)`, the complete logical leaf order is
`[x, bias, 0.5, out]`.

### Bind the CATLASS Python call and build the tree

`tla.compile` binds positional arguments, keyword arguments, and defaults by function signature through `_bind_kernel_call_args()`, separates compilation options, and passes the actual arguments as-is to lowering. A call without arguments uses `type_args=None`;
a call containing None or an empty container still keeps the corresponding actual argument. Whether the types and structures are legal is decided by lowering and the argument tree.
Only a top-level `Constexpr` is removed from the launch signature; an ordinary zero-leaf structure still keeps its logical position.

`build_runtime_argument_tree()` builds a tree for each runtime top-level argument. Containers provide metadata and children through
`NodeType.to_iterable()`, and unified traversal handles recursion, paths, and cycle checks.
NamedTuple is recognized before a plain tuple so as to keep the concrete type. Field-level Constexpr and Unit
remain in the tree but generate no runtime binding.

### Allocate MLIR arguments and reconstruct objects

`_build_runtime_physical_argument_layout()` in `execution_lowering.py`
allocates block arguments, that is, the device function's formal parameters, in binding order.

An ordinary Tensor or scalar allocates one argument; Dynamic-GM allocates three;
Constexpr/Unit allocate none. A Tensor binding is converted to an indexable proxy, and a scalar to the corresponding
Numeric value; the tree then reconstructs tuple/list/NamedTuple/dataclass.

Therefore, `aux` when compiling the user function body is:

```text
(bias_proxy, [scalar_proxy, None])
```

`aux[0][0]` accesses the Tensor proxy corresponding to the device argument, and the operation generates TLA IR.
Python container reconstruction happens during compilation.

A dataclass is reconstructed by calling `cls(**fields)` with all declared fields, so the constructor must accept these field keywords.
Therefore, `field(init=False)` using the auto-generated constructor does not satisfy the reconstruction convention.
Declaring a derived property as a field is only a necessary condition; the constructor and the `__post_init__` and other logic it calls are also
executed at compile time and must be able to handle the reconstructed Tensor/Numeric values. Reading a field may use the class default.

### Generate artifacts and the ABI description

After the TLA IR is lowered, TypeBridge generates
`KernelAbiLayout` from the lowered argument types and the current backend calling convention, and the backend compiler generates the device binary. The layout is derived by TypeBridge and is not the final binary ABI manifest exported by hivmc;
TypeBridge and the host packer must jointly follow the backend calling convention.
The Frontend block arguments and the physical fields do not always correspond one-to-one:
a memref may continue to expand into multiple address, size, and stride fields.

The host packer prepares field groups and packers according to `KernelAbiLayout`, determining the payload size and field positions.

### Replay the current arguments and launch

`ExecutionArgs`'s tree path first validates the number of Python logical arguments, then replays the current objects according to the compile-time tree.
When all arguments are ordinary Tensors/scalars, each top-level argument is one runtime leaf and can be handed directly to the prepared packer to validate the count, type, and range and pack.

Container replay calls `to_iterable(value, expected_metadata)`, using the saved metadata to read the current children
and check the concrete type, length, and None/Unit positions. A dataclass reads values by the saved field order through
`getattr()`, and an unreadable declared field or an extra instance field reports an error.
Constexpr fields do not enter the payload and do not participate in launch-value comparison; after changing the static configuration you must compile again.
The traversal function maintains paths and a cycle-detection set, sharing one leaf output list.

After flattening, the existing launch adapter is applied, and then the prepared packer writes into the buffer in ABI order.
The adapter only converts individual launch leaves and does not participate in tree building; Numeric values and providers that already have `__c_pointers__()`
keep their original values. The kind, bit width, and range of pointer/scalar are checked by the packer; memref
field groups are extracted through `build_memref_launch_fields()` and checked for the canonical field count and encoding.
Providers are integrated through these ABI interfaces without restricting their Python class.

The underlying Tensor checks its binding state when extracting a pointer or descriptor, and descriptor extraction also checks for a non-empty shape and a
supported rank. Addresses, scalar values, and dynamic sizes come from the current call.
The launcher does not compare the complete shape, stride, dtype, or layout item by item; the caller is still responsible for satisfying
the static type and layout contract of the compiled kernel, and violating the constraints may cause wrong results or out-of-bounds access.

## Physical Mapping of Dynamic-GM

Dynamic-GM is still one logical Tensor; it needs to pass the dynamic shape, stride, and origin:

| Level | Ordinary Tensor | Dynamic-GM |
| --- | --- | --- |
| Argument tree | one Tensor leaf | one Dynamic-GM leaf |
| Frontend block arguments | one Tensor argument | one dynamic memref and two origin indices |
| Final host payload | a pointer or static memref field group | a canonical descriptor field group |

`_materialize_tree_dynamic_gm_descriptors()` constructs descriptors using the dynamic formal parameters,
and `_rebuild_tree_argument_proxies()` puts the Tensor proxies back into the original structure.

Under the hivmc mixed-entry calling convention used by this Python, an ordinary static GM memref also expands into a
rank-R descriptor. TypeBridge and the host packer must jointly follow:

- Dynamic-GM: the 11 fields of a unified rank-4 memref, plus two origins, for 13 values in total.
- Static rank-R memref: allocated, aligned, offset, R sizes, R strides,
  for `3 + 2R` values in total.
- Pure static pointer entry: continue to pass a single address.

The host Tensor's `build_memref_launch_fields()` provides a unified 13-value tuple.
The packer preparation stage validates the static rank (1–4), field order, width, and grouping, and saves the field selection indices.
For example, a rank-1 static memref selects indices `(0, 1, 2, 3, 7)`, not the first five.

Dynamic-GM directly packs all 13 values; multiple descriptors form independent field groups respectively.

Thus the nested position only affects the logical path and does not change the descriptor rules for that Tensor.
For a runnable example, see [mixed_memref_arguments.py](../../../../../../examples/python/tla_dsl/dsl_tutorials/structured_arguments/mixed_memref_arguments.py).

## Cache and Binding Lifecycle

```text
current compile arguments → current argument tree and TLA IR
                       ↓
            query the artifact cache by IR, options, and toolchain
                       ↓
            device binary + KernelAbiLayout
                       ↓
            combine with this call's signature and argument tree → compiled object
```

Both in-memory and disk hits use the argument bindings of the current request and do not reuse the CATLASS Python type template of an old request.
tuple/list or different dataclasses generating the same IR can share the device artifact, but each validates its own structure.

Tensor address, version, and contents do not enter the artifact key. Static field values are kept by reference in the argument tree and
participate in tracing; after changing the static configuration, compile again, and an existing compiled object continues to use the original specialized code.
Compatibility markers of the device ABI and cache format isolate incompatible artifacts.

The NamedTuple/dataclass validation of an existing compiled object uses the concrete type identity of the current process;
the persistent cache does not encode Python type addresses. A legal new compile request can bind its own same-named type and reuse
the same device artifact.
